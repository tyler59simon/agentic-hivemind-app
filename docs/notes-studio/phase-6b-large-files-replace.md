# NS-6B: large files and replace in files

Read [README.md](README.md) and [phase-5-history.md](phase-5-history.md) first. This phase opens files too big for the editor (and binary files) in a fast viewer, follows growing logs, shows a hex view, and adds find and replace across a folder or notebook with a preview of every change.

## Changes from the NS-0 review

These rules come from the Codex review of the design ([reviews/ns0-codex-review.md](reviews/ns0-codex-review.md)). Where the text below says otherwise, these win.

- `regex` is a direct dependency (W2). Folder replace runs `files::guard` on every file it writes and skips protected ones (S2).

## Changes from the code survey before NS-6B

Claude surveyed main on 2026-11-22 (after NS-6A). Where the sections below say otherwise, these win. At the user's request this phase has no Codex review; Claude reviews the diff.

- **Which files open where.** NS-1B already opens text files up to 64 MB (`files::MAX_READ`) editable, and nobody asked to take that away, so it stays: there is no new read-only band between 8 and 64 MB. Files over 64 MB, and files NS-1B decodes as binary, open in the large file viewer instead of the "too large to edit" error. Any file tab also gets **Open in large file viewer** and **Hex view** in its menu.
- **Viewer handles** live in Rust state keyed by a handle id, opened through the same containment as `file_read` (`inside()` for notebook files, the open grant for loose files), read with read, write and delete sharing so a log writer and a rotation are never blocked. Closing the tab closes the handle; handles left over from a closed window are closed when the window goes.
- **Find in files** searches notebooks and folders registered in Hivemind only (not arbitrary paths), skips what `ignore` skips plus `.git`, `.hivemind`, binaries and files over 8 MB, and stops at 10,000 matches with a note.
- **Replace** writes each file through the same path as `file_save`: containment, `files::guard` (protected files are listed as skipped), the preview's sha256 as the precondition, an NS-5 snapshot with source `replace` before the write, the original encoding and line endings kept, and the NS-4A index told through `touched`. A file with unsaved edits open in a tab is skipped and listed. **Undo all** restores each file's pre-replace snapshot with the post-replace hash as the precondition, so a file changed after the replace is skipped, not overwritten.
- `regex` and `ignore` become direct dependencies.

## 1. What the user sees

- Files over about 8 MB open read-only in the editor up to 64 MB; above 64 MB, and binary files, open in the **large file viewer**: line numbers, jump to line, regex search with next and previous, copy lines, word wrap off. It opens instantly and indexes in the background with a progress bar.
- **Follow** (tail -f): the view sticks to the end as the file grows; a truncated or rotated file is re-indexed.
- **Hex view** for any file: offset, hex bytes, text column, jump to offset, search bytes.
- **Find in files** (palette, and a notebook or folder context menu): pattern (text or regex, case, whole word), include and exclude globs, the folder or notebook; results grouped by file with line previews. **Replace** shows a per-file diff with checkboxes, then applies with each file's hash precondition, a history snapshot first, and **Undo all** afterwards. A file changed since the preview is skipped and listed.

## 2. Design

- `src-tauri/src/bigfile.rs`: opens with read, write and delete sharing; a sparse line index (every 1024th line's byte offset) built on a background thread with `bigfile-progress` events; `bigfile_lines(handle, first, count)` decodes windows on demand (UTF-16 aware, encoding from NS-1B detection); `bigfile_search(handle, pattern, from, direction)` streams with `regex` over decoded windows; `bigfile_bytes(handle, offset, len)` for hex. Follow: a watcher plus a 500 ms size poll; growth indexes the new bytes and emits `bigfile-grew`; shrink or replace re-indexes. Handles close when the tab closes.
- Frontend: a virtual list with fixed row height (no CodeMirror, no new dependency) in `BigFileView.tsx`; `HexView.tsx` likewise.
- `src-tauri/src/replace.rs`: walk with the `ignore` crate (respects `.gitignore`, skips `.git`, `.hivemind`, binaries and files over 8 MB), match per file with encoding detection, build a preview `{ path, sha256, hunks }`, apply with `file_save`-equivalent preconditions and `history` snapshots, record an undo set.

## 3. Tests and exit

cargo: line index over generated files (LF, CRLF, UTF-16, no trailing newline), a gated 200 MB file in a temp folder, growth and rotation, regex across window boundaries, replace preview and apply, a file changed between preview and apply is skipped, undo all. Exit: a 200 MB log opens in under a second, searches and follows; replace in files never overwrites a changed file; Memory regression pass.

## 4. Shipped

Code landed on 2026-11-22: Hivemind `631df54`, with the fixes from Claude's review and UI pass. At the user's request this phase had no Codex review; Claude reviewed the diff.

**Rust**
- `src-tauri/src/bigfile.rs`: the viewer. A handle (`Viewers`, keyed by a random id and the window that opened it) holds one file, opened with read, write and delete sharing, so another program can write, rename and delete it while it is open (a test does all three, and Hivemind's own `files::atomic::hold` too). A background thread builds a sparse line index (the byte offset of every 1024th line, found by counting line breaks a 4 MB chunk at a time; UTF-16 files count their two-byte breaks) and sends `bigfile-progress`. Lines are read on demand: `LineReader` goes from the nearest mark, a window at a time, and a line longer than 32 KB is cut (`cut: true`) while search sees the first 1 MB of it. Encoding comes from `files::encoding::decode` on the first 256 KB (byte order mark, UTF-16 without one, UTF-8, a legacy guess); a binary file is shown as text with its control bytes as dots. Commands: `bigfile_open` (returns the first 120 lines at once), `bigfile_lines`, `bigfile_search` (regex or plain text, case, next or previous from a line and column, wrapping, and a newer search stops an older one), `bigfile_bytes`, `bigfile_find_bytes` (hex or text bytes, both ways, windows overlapping by the needle), `bigfile_close`. Closing a handle stops its thread; a window's handles close when it is destroyed (`on_window_event`); at most 32 handles.
- Following is a 500 ms poll of the file at its path, not a watcher plus a poll: it opens the path again each time and compares size, the first 4 KB and the creation time with what it indexed. Growth is indexed from where the index stopped (`bigfile-grew`); a smaller file, other first bytes or another creation time (a rotation, or a truncate and rewrite) is indexed again from its start (`bigfile-grew` with `reset`). The first 4 KB are compared as well because Windows can give a recreated file the old creation time for a few seconds.
- `src-tauri/src/replace.rs`: find and replace in files. `preview` walks the scope with the `ignore` crate (`.gitignore`, `.ignore` and `.git/info/exclude` respected without needing a repository, hidden files and folders left out, so no `.git`, `.hivemind` or `.obsidian`, links not followed), applies the include and exclude patterns itself as gitignore-style lists (so an include pattern cannot bring back what `.gitignore` left out), skips binary files and files over 8 MB (counted, not listed), decodes each file as the editor does (`files::decode`), and lists matches as hunks with their line, the lines as they are and as they would be. Matches with no characters are left out. It stops at 10,000 matches (`capped`). A file that matches but is not editable (mixed line endings, bytes that do not decode) and a file the guard refuses are listed as skipped with the reason. `apply` takes the files and the matches left ticked, and for each file: skips it when its path has unsaved edits in a tab (the webview names them), when `studio::inside` refuses it (protected, hidden, through a link, outside the folder), or when its bytes no longer hash to the preview's hash; otherwise writes through `studio::save_kept` with source `replace` (the file as it is on disk is kept first, labelled `disk`, and the new text after the write, labelled `replace`, as for any save that is not the user's own), with the preview's hash as the save's precondition, in the file's encoding, byte order mark and line endings (`files::encode`). `undo` puts each file back from its pre-replace version, with the hash the replace wrote as the precondition, so a file changed since is skipped. The commands tell the search index about each file written (every registered notebook that holds one gets `touched`). `replace_apply` returns an undo id; the last 8 sets are kept in memory (`Undos`), and after a restart each file's History still has the versions.
- Scope: `replace_preview` and `replace_apply` take a notebook id (and optionally a folder of it, `sub`) or a folder from the user's "other folders" list (`folders::find` on the settings). Anything else is refused. A folder is checked with `Protected::check_root`.
- `studio.rs`: `inside`, `root_of`, `touched`, `save_kept` and `Change` became `pub(crate)` for the two new modules. `lib.rs`: the two modules, `AppState.bigfiles` and `replace_undos`, the nine commands, and closing a window's handles. `Cargo.toml`: `regex` and `ignore` are direct dependencies (the lock file also gains `ignore`'s own dependencies: `globset`, `bstr`, `walkdir`, `same-file`, `crossbeam-deque`, `crossbeam-epoch`).

**Deviations**
- Follow is the 500 ms poll alone; a watcher added nothing the poll does not see.
- The pre-replace snapshot is labelled `disk` and the one after the write `replace`, as `save_kept` does for every save that is not the user's own (NS-5); the phase text says a `replace` snapshot is taken before each write.
- The preview does not reuse NS-6A's `hunks.ts`: that file models `@codemirror/merge` chunks of two whole documents, and a search result is a list of single matches with their lines, which `replace.rs` produces directly.
- A binary file opens in the hex view first (the large file viewer is one tab away), since lines of a binary file are not useful.
- Find in files opens a match's page only for a notebook scope. A file in one of the "other folders" is not a notebook page and the webview cannot name it, so its results are shown but not clickable.
- Lines are split at `\n` only; a file that uses lone carriage returns (classic Mac) shows as one line.
- A line longer than 32 KB is cut when shown, and search sees the first 1 MB of a line, so a match deeper in a longer line is not found.

**Fixes after Claude's check in the dev app (webview only)**
- UI-1, the viewer did not scroll inside the pane. Nothing bounded the page's height, so `.bigfile-space` (up to 8,000,000 px) made the pane body scroll the whole page, and rows far down were drawn at their offset where `.bigfile` could not scroll to them. Now the viewer's root is `note-page file-page viewer-page` (`FileTab.tsx`), and the rule that bounds the height is `.viewer-page { height: 100%; min-height: 0; overflow: hidden; }` in `App.css`: `.pane-body` is a bounded flex item (`flex: 1; min-height: 0`), so the page is exactly as tall as it and does not grow with its rows. `.bigfile-page` is a column that fills it (`flex: 1; min-height: 0; overflow: hidden`), and `.bigfile` (also the hex view's scroller) is its only growing child (`flex: 1; min-height: 0; overflow: auto`, the old `min-height: 12rem` is gone), so it is the one thing that scrolls. `.viewer-page` comes after `.note-page` in the file, so its `min-height: 0` wins over the page's `min-height: 100%`. The window also measures `clientHeight` of a scroller that is now bounded, where before it measured 8,000,000. A test in `FileTab.bigfile.test.tsx` checks the structure for both views (page, then `.bigfile-page`, then `.bigfile`, then `.bigfile-space`) and reads those rules from `src/App.css`; it fails when `height: 100%` leaves `.viewer-page` or `min-height: 0` leaves `.bigfile`. Jump, search hits, Follow and the scaled scroll bar all move `.bigfile`'s `scrollTop`, which now has the range they compute; jsdom cannot show that, so it is for the dev app.
- UI-2, a binary file in the tree could not reach the hex view. "Other" in the tree is every file that is not a page or a known text type (the Rust walk gives `Kind::Other`); nothing else handled them. A click on one now opens a file tab (so a binary opens in the hex view), except pictures and PDFs (`png jpg jpeg gif webp avif bmp ico svg pdf`), which still open in the program Windows has for them, as before, and a Living Memory notebook's files, which are not files on disk. The file's menu gains **Open with default app** and keeps **Show in Explorer**. `NotebookTree.other.test.tsx` clicks a binary and an archive (tab, no Explorer), a picture and a PDF (Explorer, no tab) and checks the menu; it fails when a binary goes back to Explorer.
